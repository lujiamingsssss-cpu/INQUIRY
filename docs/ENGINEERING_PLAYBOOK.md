# Engineering Playbook

本手册说明如何执行根目录 `AGENTS.md`。它描述通用工程流程，不保存当前项目进度，也不替代用户的具体需求。

## 1. 为什么采用这套方式

本仓库早期五轮开发反复证明：稳定交付依赖可复现案例、最小变更、真实验证、人工检查点和可回滚路径，而不是越来越长的聊天记录或状态文档。

这套流程也对应成熟工程实践：

- [AGENTS.md](https://github.com/agentsmd/agents.md) 为编码代理提供仓库级常驻指令；
- [GitHub Spec Kit](https://github.github.com/spec-kit/index.html) 使用“规格 → 计划 → 任务 → 实现”的规格驱动流程；
- [Google Engineering Practices](https://google.github.io/eng-practices/) 强调小而完整的变更、同行审查和测试随代码同行；
- [GitHub分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges/managing-protected-branches/about-protected-branches) 通过必需检查约束合并；
- [MADR](https://adr.github.io/madr/) 和 [Google Cloud ADR指南](https://docs.cloud.google.com/architecture/architecture-decision-records) 用轻量记录保存重要决定的背景与后果。

本项目只采用适合小型私人项目的最小组合，不引入完整企业流程。

## 2. 最小任务路由

本项目不采用企业级工单分类、复杂度分数或风险矩阵。Codex 只做足以选择流程的判断。

### 2.1 是否只读

如果用户只要求解释、调研、诊断、审查或状态报告，按 Read-only 处理，不修改文件或外部状态。

### 2.2 需要改动时选择一个类型

| 类型 | 判断标准 | 核心流程 |
|---|---|---|
| Bug | 已有行为与明确预期不一致 | 复现、根因、失败回归测试、最小修复、验证 |
| Feature | 增加或改变用户可观察能力 | 场景、范围、方案、验收案例、最小实现、验证 |
| Task | 重构、依赖、测试、文档、构建、数据或运行操作 | 明确目标，采用与实际风险相称的规则和验证 |

### 2.3 只判断两个附加条件

- **Long?** 是否命中 `AGENTS.md` 的长任务条件；
- **High-risk?** 是否涉及数据、索引、安全、权限、外部写入、部署、不可逆迁移或可能破坏当前可用版本。

Long 或 High-risk 任一为“是”，都必须创建 `CURRENT_WORK.md`。High-risk 还必须设置人工批准点和回滚路径。

不使用 Small/Standard/Long 等多档评分，不使用 Low/Normal/High/Emergency 风险等级，也不由 Codex 判断业务优先级。除非分类会触发建档、审批或停止，Codex 无需把内部分类过程输出给用户。

发现新证据后可以升级控制强度；一旦升级为 Long 或 High-risk，必须暂停实现并先创建 `CURRENT_WORK.md`。

## 3. 通用启动检查

每次开发或修复开始时：

1. 用一句话复述要解决的问题；
2. 读取相关代码、测试、配置和最近 Git 变更；
3. 检查工作树，区分用户改动与当前任务；
4. 写出明确范围和非目标；
5. 确定什么证据能够证明完成；
6. 判断是否需要调研、设计审批、`CURRENT_WORK.md` 或 ADR；
7. 在没有失败案例、验收标准或批准方案时，不进入实现。

## 4. CURRENT_WORK.md

### 4.1 创建时机

创建条件以 `AGENTS.md` 为准。它是活动任务的临时控制面，不是新的项目基线。

### 4.2 固定模板

创建根目录 `CURRENT_WORK.md` 时使用以下结构：

```markdown
# Current Work: <任务名称>

Status: active
Started: <YYYY-MM-DD>
Branch/Worktree: <分支和工作树>

## Objective
一句话说明要实现的结果。

## Scope
- 本次必须完成的内容。

## Non-goals
- 明确不做的内容。

## Starting Evidence
- 当前提交、工作树和测试基线。
- 已复现的问题或已批准的需求。

## Acceptance Evidence
- 能自动验证的案例、指标或输出。
- 必须人工确认的结果。

## Milestones
- [ ] M1：案例或复现基线
- [ ] M2：最小实现
- [ ] M3：相关与全量回归
- [ ] M4：真实动态验证与收口

## Decisions and Constraints
- 已确认的决定、禁止项和人工批准点。

## Findings and Failures
- 关键根因、失败证据和被否决方案。

## Verification Log
- 日期、命令、退出状态和结论。

## Next Action
后续任务可以直接执行的唯一下一步。
```

### 4.3 更新规则

- 只在里程碑、根因、范围、审批点或下一动作变化时更新；
- 每条记录必须区分事实、推断和待确认内容；
- 不能把测试尚未通过写成已经完成；
- 跨会话前必须记录当前 Git 状态、失败点和唯一下一动作；
- 当前任务完成后先提炼长期资产，再删除该文件。

### 4.4 冲突处理

若发现一个与当前请求无关的活动 `CURRENT_WORK.md`：

- 不覆盖、不删除、不擅自继续；
- 检查是否进入错误分支或工作树；
- 向用户说明现有任务名称和冲突；
- 由用户选择继续旧任务、切换工作树或结束旧任务。

## 5. 新功能开发流程

### 5.1 需求与场景

先回答：

- 谁使用；
- 当前遇到什么真实问题；
- 不做会怎样；
- 成功后用户能完成什么；
- 哪些内容明确不属于本次范围。

用户表述可能不专业时，应从目标和真实行为理解需求，但不能借“优化”扩大授权。

### 5.2 调研与方案

需要新依赖、框架、算法、外部服务或新架构时，先检查：

1. 仓库已有能力；
2. 官方文档和成熟实现；
3. 维护状态、许可证、依赖规模和运行成本；
4. 采用、薄封装、组合或自建的取舍；
5. 当前固定失败案例是否真的需要它。

至少比较两个合理方案。推荐方案必须说明为什么适合当前规模。

### 5.3 设计审批

以下变更必须在编码前展示设计并获得批准：

- 新页面或明显改变用户流程；
- 新数据库、索引、模型或外部服务；
- 数据格式、权限或安全边界变化；
- 会产生持续费用或不可逆迁移；
- 用户明确要求先看方案、线框或计划。

### 5.4 Golden-first

实现前先建立验收证据：

- 可回答案例指定准确预期；
- 不可回答案例明确禁止的输出；
- 现有案例和目标不得为了新实现而漂移；
- 先记录当前基线，再修改实现；
- 不把不相关数据绑定为方便通过的目标。

### 5.5 实现与验证

按最小自洽阶段实现。每阶段都应保持系统可运行，并执行：

1. 新案例或失败测试；
2. 最小实现；
3. 专项测试；
4. 相关模块测试；
5. 全量测试；
6. 与用户真实路径一致的动态验证；
7. 差异和复杂度审计。

## 6. Bug 修复流程

### 6.1 复现

记录：

- 精确输入和环境；
- 预期结果；
- 实际结果；
- 是否稳定复现；
- 首次出现的版本或相关提交；
- 日志、截图、堆栈或状态证据。

无法复现时继续缩小变量，不直接提交猜测性修复。

### 6.2 根因

区分症状与根因。使用单变量实验、日志、最小复现或已有测试定位故障发生层。对间歇性问题先判断是否为资源释放、并发、环境、时序或外部依赖，再决定是否允许有界重试。

### 6.3 回归测试

回归测试必须：

- 在修复前因原问题失败；
- 失败信息能够指向被修复行为；
- 在修复后通过；
- 不依赖无关网络、时间或环境偶然性；
- 保留用户可观察行为，而不是锁定内部实现细节。

### 6.4 最小修复

只修改根因路径。若发现相邻重构需求，除非不处理就无法安全修复，否则记录为独立任务。

### 6.5 验证层次

1. 原始复现路径；
2. 新回归测试；
3. 相关测试；
4. 全量测试；
5. 真实环境路径；
6. 安全、性能、兼容性和回滚检查。

## 7. 验证矩阵

| 变更 | 最低验证 |
|---|---|
| 纯文档 | 文件存在、链接/术语、范围和 Git 差异 |
| 纯重构 | 现有相关测试与全量测试，证明行为不变 |
| 业务逻辑 | 新测试、相关测试、全量测试 |
| UI | 自动化测试、真实浏览器正负路径、关键交互 |
| 模型/RAG | 固定 golden、真实模型调用、证据门禁负例 |
| PDF/文件 | 解析、真实页面、路径和元数据验证 |
| 数据/索引 | 预检、暂存构建、完整性、切换、失败保持和回滚 |
| 外部集成 | 沙箱或受控目标、错误路径、权限和重复调用安全 |

测试命令以仓库当前配置为准。历史命令和结果必须先核对仍适用，不能机械复制。

## 8. 复杂度自省

在调研后、设计后、关键实现后和最终验收前分别检查：

- 新代码是否由当前验收案例直接需要；
- 是否存在更简单的成熟方案；
- 是否增加第二事实源、第二数据库或第二流程；
- 是否预建没有调用方的接口；
- 是否把一次性 Demo 做成生产平台；
- 是否能删除某层而仍满足全部验收；
- 是否为了表面成功降低证据或安全门槛。

无法用失败案例或明确要求说明必要性的复杂度不进入当前变更。

## 9. 决策记录与运行手册

### 9.1 ADR

只有决定会长期影响多个模块，并且难以撤销、不记录原因很可能导致错误回退时，才按需创建 ADR。ADR只保存背景、备选方案、决定、后果和回退条件，不保存任务进度；普通功能、Bug、局部重构和容易撤销的选择不创建 ADR。

### 9.2 Runbook

只有同时满足以下条件才创建运行手册：

- 操作以后会重复；
- 包含容易遗漏的顺序、检查点或回滚；
- 已至少真实成功执行一次；
- 自动化暂时不比人工步骤更可靠或更经济。

Runbook记录命令、输入、预检、停止点、成功标准和回滚，不建立第二套产品需求。

## 10. 收口

完成前必须：

1. 在当前工作状态运行新鲜验证；
2. 检查失败数、退出码和真实输出；
3. 核对 Git 差异只包含授权范围；
4. 说明未运行的验证及原因；
5. 清理临时进程、测试文件和无用产物；
6. 对长任务提炼长期资产并删除 `CURRENT_WORK.md`；
7. 未经授权不提交、不推送、不部署；
8. 最终答复只报告有证据支持的完成状态、重要限制和下一步。
